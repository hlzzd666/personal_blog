# 个人博客的整体设计思路以及后面可能的规划

这个博客不是先把页面设计完，再去想里面放什么。它是边写边长出来的。

刚开始，我只想要一个能放文章的地方。后来文章需要分类、标签和专题，开发过程又想留下短动态；再往后，我给它加上了每日学习、文章统计大屏和 3D 展馆。功能越堆越多之后，我才开始认真想：这个博客到底要服务什么，哪些东西应该继续做，哪些东西只是暂时觉得有趣。

现在回头看，它大致有四个方向：让内容容易写，让文章容易读，让管理尽量省事，再给这个个人项目留一点可以慢慢玩的空间。

## 先确定它是什么

我不想把博客做成一个只有文章列表的模板站，也没打算一开始就做成多人协作的内容平台。它首先是一个个人记录工具，技术文章、项目复盘、学习记录和一些没那么完整的想法，都应该有自己的位置。

所以“内容”排在“功能”前面。页面可以慢慢改，数据库表也可以迁移，但写下来的东西最好能稳定保存，几年后还能找到。

这个判断影响了很多细节：文章正文保存为 Markdown，文章有稳定的别名，专题只负责组织阅读顺序，短动态单独走时间线。每日学习虽然通过 AI 生成，但最终也会落到文章模型里，避免前台出现一套完全不同的阅读方式。

## 一个仓库，三个应用

项目现在是一个 monorepo，主要分成三个部分：

- `web/` 是访客看到的博客前台，负责首页、文章、专题、短动态、关于我、留言板、展馆和文章大屏。
- `admin/` 是管理后台，负责文章编辑、分类与标签、专题、媒体、每日学习、留言审核和站点设置。
- `backend/` 是 FastAPI 后端，负责 API、数据库、权限、业务规则和定时任务。

前台和后台不直接共享数据库模型。它们通过版本化的 `/api/v1` 接口通信，后端再按路由、服务、模型的方向组织代码：路由处理请求，服务处理业务，模型对应数据表。这个分层听起来普通，但对个人项目很有用。以后页面重做，至少不用把数据库查询散在每个 Vue 页面里。

数据层使用 MySQL，数据库变更通过 Alembic migration 管理。Redis 用在 Session、限流和部分运行锁上。部署时还要考虑上传目录、对象存储和反向代理，这些事情不太显眼，却决定了博客能不能稳定运行。

## 前台先解决阅读问题

前台采用航海日志的视觉方向。这个选择不是为了把每个按钮都做成船舵，而是因为它能给页面一条比较稳定的线索：文章像航行记录，专题像航线，展馆像船舱里的收藏。

首页要让人尽快知道三件事：这里是谁的博客，最近写了什么，下一步可以去哪里。文章详情页则尽量安静，目录、代码、图片、阅读进度和返回路径都围绕阅读展开。文章列表提供搜索、分类、标签和自动续载，避免访客只能按时间一篇篇翻。

文章大屏是一个偏实验性的页面。它把文章数量、分类、标签、专题、篇幅、发布日历和访客统计放在一张固定画布里，还能点进文章明细。它不参与日常阅读，却很适合让我观察自己的写作习惯：某个月是不是只写了同一类东西，文章是不是越来越短，哪些专题一直没有继续。

3D 展馆的定位也比较明确。它是博客的一个可探索入口，不承担文章阅读任务。桌面端可以在船舱里漫游、查看人物档案，小屏、WebGL 不可用或指针锁定失败时，则回退到二维馆藏列表。这样做有点麻烦，但我不想让一个视觉实验挡住基本内容。

## 后台优先解决“写得下去”

后台文章页现在可以维护标题、别名、摘要、封面、作者、来源、发布时间、分类、标签和专题，正文使用 Markdown 编辑器。文章写入后直接进入归档，暂时没有草稿状态。

这个决定有利有弊。少一个状态，发布流程会短一些；代价是写到一半的内容没有站内保存区，只能依靠本地文件或编辑器草稿。等博客真正形成稳定更新节奏后，我可能会补上草稿和预览，但那会牵涉文章列表、搜索、RSS、站点地图和权限判断，不能只在表里加一个 `status` 字段就结束。

分类和标签使用单独的管理页面。分类是单选，标签是多选；被文章引用的项目不能直接删除，避免整理分类时把历史文章弄坏。专题删除时只解除文章关联，不删除文章本身。这些规则没有视觉效果，却比再加一个装饰页面实用得多。

留言板也走审核流程。访客提交的内容先进入待审核状态，后台通过后才会公开。接口还会做限流、重复内容检测和纯文本校验。个人博客不一定会遇到很大的流量，但公开表单还是要有基本的边界。

## 自动内容要有自己的位置

每日学习模块是我对自动化的一次尝试。后台可以设置发布周期、时间、主题、模型、提示词、题目数量、文章模板、分类、标签和专题。每次任务都会留下运行日期、状态、尝试次数、错误原因和生成文章的 ID。

我没有把它做成另一套文章系统。任务成功后，问答内容会生成普通文章；公开文章列表会把每日学习记录从常规归档中筛掉，避免自动内容占满首页。这样做的好处是生成过程和阅读过程分开，前台仍然只有一种文章详情页。

这套功能现在还谈不上完全自动。模型会答错，接口会超时，提示词也需要反复调整。它更像一个可以观察的实验：哪些学习内容适合批量生成，哪些内容必须自己查资料、自己写。

## 数据和权限不能最后再补

公开接口允许匿名读取文章、专题、短动态和部分站点资料。后台写入则依赖服务端 Session、HttpOnly Cookie 和 CSRF 校验。文章点赞还会通过匿名访客标识去重，访客记录、留言和位置展示也分别处理隐私边界。

我在开发中越来越在意这一层，因为“先把页面做出来，安全以后再说”通常会变成“以后很难再改”。比如文章删除要考虑专题关联，媒体清理要确认文件没有被内容引用，留言审核要避免未审核文本直接进入前台。功能之间是连着的，数据模型也一样。

## 接下来可能做什么

后面的规划不会按“把所有想法都做一遍”来排。我更想按使用频率和维护成本来排，先把已经存在的功能用起来。

### 先恢复真实的更新节奏

博客最近最缺的不是新模块，而是新文章。短期内我会先写项目复盘、功能取舍和实际遇到的问题，把现有的文章、专题和短动态真正用起来。只有内容重新流动起来，统计大屏和推荐逻辑才有意义。

### 给文章增加更可靠的编辑流程

草稿、预览、定时发布和修订记录都在候选列表里。优先级不会很高，除非我开始经常在后台编辑长文章，或者需要在发布前反复校对。真要做，会先把文章状态和公开查询规则理清，再处理后台界面。

### 把搜索和内容关系做得更好

现在的搜索已经能匹配标题、别名、摘要和 Markdown 正文，专题也有上下篇和相关推荐。以后可以继续观察搜索结果是否真的有用，再决定要不要做全文索引、相关度排序或更细的筛选。搜索不该为了看起来高级而变复杂。

### 继续打磨部署和备份

个人博客最怕的是本地开发时一切正常，服务器出问题后才发现没有清晰的备份和恢复路径。后面会继续整理上传目录、数据库备份、日志、迁移和发布流程，把部署文档写到别人也能照着执行的程度。

### 保留一小块实验区

3D 展馆、文章大屏和每日学习都属于实验。它们不一定会一直保留现在的形态，也不一定都值得继续扩展。我的标准会简单一点：它是否帮助我记录或理解内容，是否值得承担它的维护成本。如果答案连续几次都是“不确定”，就先放一放。

## 最后还是回到写作

这个博客现在有不少页面和数据表，偶尔看起来像一个小型内容产品。但对我来说，它仍然是一个写东西的地方。

整体设计的目标，是让文章有稳定的存放位置，让短想法不必硬写成长文，让专题可以串起已经写完的内容，也让一些自动化实验不会打扰正常阅读。后面的规划会随着真实使用调整，先做那些能让我继续写下去的事情。

如果下一篇文章还没想好，我会先打开后台，写下一件最近确实做过的事。博客的规划可以慢慢改，记录不必等到一切都准备好。
